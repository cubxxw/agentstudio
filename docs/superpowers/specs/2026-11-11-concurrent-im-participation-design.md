# Concurrent IM reading, silence and reactions

The owner approved the preceding queue/group analysis and requested implementation: every available group agent receives messages independently, reads the conversation without waiting for other models to decide whether to speak, and chooses a response according to its own persona. IM supports silence and message reactions.

## Behavior and decisions

- Keep one durable SQLite inbox and one app-owned worker, with a bounded pool of three independent invocations (implementation choice for this shared Mac). Delivery to all eligible members is atomic with accepting the owner message. Delivery is not evidence of reading or understanding.
- Preserve per-conversation/per-agent order. Independent stateless local CLI invocations may run concurrently even when they use the same executable. A2A/MCP bindings sharing a URL serialize conservatively across contacts and conversations; unknown external outcomes remain barriers when either the new or prior invocation is contact chat. Independently approved legacy task-to-task behavior remains compatible. Original-task read-only reconciliation crosses historical barriers while retaining active-session exclusion. Legacy task planning retains exclusive execution because it can change executor after planning. Role preparation can run independently.
- Record the exact visible message IDs supplied to each invocation and its read timestamp. A successful response acknowledges that snapshot; starting/submitting alone never produces a read receipt. Reactions and silence acknowledge reading without fabricating a text message or document artifact. Failed/cancelled invocations never become silence.
- Raft-inspired reading means checking the currently visible inbox at dispatch, including replies already published to the same owner message, while excluding later owner messages, pre-join history, removed-member publications and unrelated chats. Do not wait for unfinished peers. Snapshot the visible context once for an invocation; do not inject changing requirements into an in-flight request. Later owner messages get their own ordered runs. Record newly arrived messages as pending for later reads, without claiming the completed response saw them.
- The workspace IM setting `allowSilence` defaults true and is versioned. Group information offers an optional override (inherit/allow/require response). Accepted runs freeze their effective setting. Explicit `always` remains mandatory response; manual/mention routing remains supported. Ordinary DMs can still use plain Markdown; the participation envelope is optional there. Auto groups retain the strict validated envelope.
- Local agents may return `{action:"reply",text}`, `{action:"reaction",emoji}`, or `{action:"silence",reason}`. A reaction targets the run's own input message, uses one supported emoji, stores actor identity and run ID, and is applied once. Owner reactions are reversible and idempotent. Remote ordinary text stays compatible; supported envelopes may be consumed only on contact-chat runs, never tool/task receipts.
- Silence disabled rejects a silence envelope; it is never silently converted to success. Reaction counts as an actual response. Do not publish raw protocol JSON as a progress preview.
- Group IM does not create one queued/waiting reply bubble for every member. Show one quiet group activity status and completed text/reaction results. Errors and precise stop controls remain available in execution records. Preserve ordinary DM follow-up feedback with accurate waiting wording.
- Agent replies/reactions do not recursively wake peers. This change does not introduce autonomous team task delegation, consensus voting, file-edit permissions, external mutation authority or a general distributed Raft implementation.

## Alternatives

The owner chose independent reading with optional participation over the existing global serial queue. A central next-speaker selector adds a coordinator call to every message and conflicts with default independent reading. Unbounded invocations would ignore the shared host and service sessions; use bounded concurrency and explicit session lanes instead. Per-message turn-taking and bounded task handoffs remain future extensions.
